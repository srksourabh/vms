1. How we are thinking about this

A mall gate is not a website with a login. It is a physical exchange: a person, a card, a host, a time. The product is built so that:

  • The employee books. They already know who is coming. They type name, mobile, email, date and time. The system mints an OTP.
  • The visitor arrives with that OTP. They do not need an app. They speak the six digits.
  • Security proves identity. ID scan (or typed last-four if the camera cannot read the card), live photograph, then a physical badge number typed in. Only then is the person checked in.
  • The badge is an asset. It is issued at entry and demanded at exit. Typing the returned number closes the visit and frees the badge for the next person.
  • Walk-ins still have a host. Security captures the request; the employee approves; an OTP is mailed to the desk; the guard admits.
  • Admin sees everything and writes almost nothing on visits. Adding/removing people is an admin job. Changing a visit’s status is a gate job. Blacklist removal needs a second person (CEO).

The deployment model is on-premise: Postgres, Auth, files and the app process all run on a machine the mall owns. The Windows .exe on a guard PC is a thin client. The phone PWA is the same app, installed on the home screen, used by employees to request a visitor without walking to a desktop.

2. End-to-end user flow

  1. Pre-register. Employee (staff) signs in, opens Pre-Register a Visitor, enters name / mobile / email / expected slot. The server returns a 6-digit OTP and a VIS-YYYYMMDD-NNNN.
  2. Visitor is coming. They receive the OTP by email (and an SMS row is written for the GSM gateway). They need no account.
  3. Formalities at security. Guard opens Scan Pass, types the OTP, sees host, department, purpose, phone.
  4. Badge issued. Guard scans (or types) the ID, captures a photograph, types the physical card number (e.g. B-218), presses Check In.
  5. Visitor entering. Status becomes checked_in. The host is notified in-app. The person is on Entry & Exit → Checked In and on any fire-marshal list.
  6. Time of return. Guard types the returned badge number. The confirm dialog names that number; the tick is mandatory. Check-out frees the badge.

3. How Quest Mall benefits

  • The book is replaced, not copied. Admin Visitors Log is the register: on screen, CSV, and print. Seventeen columns, IST timestamps, no zone suffix games.
  • Who is inside is a fact, not a guess. Open visits are never date-bounded, so a contractor from yesterday is still on the list at 00:10.
  • One person, one presence. A unique index refuses a second checked_in row for the same visitor.
  • Watchlist is not a rumour. Flagging is one admin. Unflagging is two people. The gate keeps refusing while a request sits with the CEO.
  • Badges stop vanishing. A number is typed in and typed out. The next visitor can receive the same card immediately.
  • Brand. Quest gold / navy, mall logo, no vendor chrome on the guard screen.
  • PII stays in the building — photos in a private bucket, ID numbers stored as last-four only.

We chose premises because the customer’s explicit constraint was that visitor data must not go outside. The same codebase can point at a hosted Supabase later if they change that constraint — it is an env file, not a rewrite.

6. How the database is installed inside the premises

  1. Install Docker Desktop (Windows server) or Docker Engine (Linux).
  2. Copy this repository onto that machine. Node 20+ is required.
  3. From the repo: npx supabase start. That boots Postgres (port 54322), Auth, PostgREST, Realtime, Storage, and Mailpit. Migrations apply on first boot. All of it is containers on that host.
  4. Put the printed keys from npx supabase status into .env (VITE_SUPABASE_URL=http://127.0.0.1:54321 plus the local anon and service-role JWTs). Those keys never leave the machine.
  5. npm run seed creates departments and the first users (change passwords before a real day).
  6. Serve the app: npm run dev for demo, or npm run build then npx vite preview --host 0.0.0.0 --port 5173 for a shift. Windows: installer/windows/Start-Server.bat.
  7. Guards double-click Secure Gate. The splash shows a green light when the app and Auth health check both succeed, then the login page.
  8. Employees on phones open the same URL, use the browser’s Add to Home Screen — that is the PWA. They can pre-register a visitor from the floor.

Nothing in that list is a SaaS signup. Postgres data is a Docker volume on that PC. Back it up like any other database: snapshot the volume nightly to a second disk the mall already owns.

Helper: scripts/onprem-up.sh (Linux) · installer/windows/install.ps1 (Windows).

7. Desktop .exe and mobile PWA

Windows

desktop/ is an Electron shell. It does not ship the database. It pings the on-prem server and refuses to open login until both the web app and Auth answer — that is the green light. Build on a Windows PC:

cd desktop
npm install
npm run pack:win

That yields SecureGate-Portable.exe (double-click, no install). Compile installer/windows/SecureGate.iss in Inno Setup for a Start Menu installer that also drops “Start Secure Gate server”.

Mobile PWA

Production builds register /sw.js and advertise /manifest.webmanifest. On HTTPS (or localhost) Chrome/Edge/Safari offer “Install app”. Staff land on Visitors and can pre-register. Guards should still use a desktop/tablet for the camera and badge typing — the phone is the employee request surface.

PWA install on a raw HTTP LAN IP is blocked by browsers. For phones on the mall LAN, put a reverse proxy with a local certificate (Caddy + internal CA, or mkcert) in front of port 5173. That is a go-live question, not a code change.

8. Questions to make every function live on day one

  1. Where is the server physically (UPS, lock, whose key)?
  2. LAN plan: DHCP or static for the server; can HOD phones reach it?
  3. SMTP relay, From: address, and whether OTPs may leave the building as email.
  4. SMS: skip, log-only, or a named GSM/DLT vendor with a template ID?
  5. Named Admin, HODs, guards, CEO — emails and departments.
  6. Photo retention days (default 365) and who signs that policy.
  7. Badge stock: numbered plastic cards, and the numbering scheme (we accept A-Za-z0-9- up to 20 chars).
  8. Printer: none / A6 slip / thermal. The product already prints a pass; plastic cards are typed, not printed.
  9. Backup target and restore drill date.
  10. Who is allowed to run npx supabase db reset (it wipes visits).

10. Honest limits

  • Check-in needs a photograph. A laptop without a webcam uses upload from device (already in the UI). If OCR cannot read the ID, the guard types document type, last four, and the printed name.
  • SMS is not a live modem in this box. Email is live against the on-prem relay.
  • The Windows .exe is a client. The database is Docker on the server. One PC can be both if Docker Desktop is installed on it.
